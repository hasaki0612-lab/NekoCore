# 经济、商店、Bag 与头衔

[English](../en/ECONOMY.md) | [返回 README](../../README.md)

这一页讲的是 NekoCore 里"数字怎么流动"的部分：金币从哪来、往哪去、商店怎么定价、Bag 和头衔在经济里扮演什么角色。

它不只是数字表。默认值是有设计意图的——知道那个意图，你才知道该往哪个方向调。

---

## 金币和经验的来源与去处

NekoCore 的 Coins、EXP、Level 是**同一个玩家资料系统**的三个面，不是三套独立的东西。

```text
        收入                          支出
  ┌──────────────────┐         ┌──────────────────┐
  │ 每日签到          │         │ 商店买入          │
  │ 每日任务          │  ────▶  │ 每日附魔书        │
  │ 挂机池（可选）     │         │ 头衔购买          │
  │ 管理员操作        │         │                  │
  └──────────────────┘         └──────────────────┘
```

**收入的四个来源：**

| 来源 | 默认值 | 特点 |
| --- | --- | --- |
| 每日签到 | 100 金币 + 50 EXP | 稳定、无门槛、每天一次 |
| 每日任务 | 一天全清 345 金币 + 240 EXP | 需要做点事，有难度梯度 |
| 挂机池 | 概率给 1–4 金币，固定给 EXP | 默认关闭，需要配置 |
| 管理员操作 | — | `/nekocore coins add` 等 |

**支出的两个去处：**

| 去处 | 特点 |
| --- | --- |
| 商店 | 日常消耗，价格跨度很大（3 金币的火把到 1800 的不祥试炼钥匙） |
| 头衔 | 大额储蓄目标（2500 / 7500 / 20000） |

**等级的作用：** 等级本身不直接花钱，但它解锁 Bag 的槽位（默认 10 级开 27 号槽、25 级开 36 号槽）。所以经验也是有实际价值的进度，不只是个数字。

## 这套默认值设计成什么感觉？

这是这一页最值得读的一节。

默认的经济数值**不是为大型服务器调的**。它的目标场景是：**朋友服、小社区服，十来个人到几十个人，大家认识彼此，经济是用来提供节奏感的，不是用来制造竞争的。**

### 算一笔账

假设一个玩家每天上线、签到、做完九个任务：

```text
签到              100 金币
任务全清          345 金币
                ─────────
一天              445 金币
一周             3115 金币
```

对照头衔的价格：

| 头衔 | 价格 | 全勤玩家大概需要 |
| --- | --- | --- |
| Yuki | 2500 | 约 6 天 |
| Momo | 7500 | 约 17 天 |
| Neko | 20000 | 约 45 天 |

**这个曲线的意思是：** 第一档头衔一周内能拿到，给新玩家一个看得见的短期目标；最高档需要一个月以上，是一个长期陪伴的象征，而不是一周就能刷满的东西。

如果你希望玩家更快拿到头衔，把签到和任务奖励调高就行——但要想清楚代价：收入提高之后，商店里的东西也会显得便宜，你可能需要一起调价格。

### 什么时候该调整

默认值在这些情况下会不太合适：

| 你的情况 | 建议方向 |
| --- | --- |
| 服务器有高效的刷怪塔或农场 | 给易刷商品加 `buy-limit`，或者单独关掉它们的 `sell` |
| 在线人数多、交易频繁 | 提高奢侈品价格，观察交易日志 |
| 玩家抱怨"赚不到钱" | 提高签到或任务奖励，而不是降低商店价格 |
| 玩家抱怨"钱没地方花" | 增加高价商品，或者提高头衔价格 |
| 你想让经济更"硬核" | 降低签到奖励，让任务成为主要来源 |

**没有通用正确答案。** 定价这件事，观察你服务器的交易日志比套公式有用得多。上线之后看一两周，你会比现在更清楚该往哪个方向调。

### 一点提醒

> 修改价格、奖励、限额**不会重写已经完成的交易**。

玩家昨天按旧价格买的东西不会被追溯补差价，昨天领的签到奖励也不会补。所以调数值最好的时机是**换日之前**，或者干脆接受"今天有一批人按旧价领了"。

## Store：109 件起步商品

Public 版保留了 109 个商品作为一个**可以直接开玩的起点**。它们分在八个分类里：

| 分类 | 大致内容 | 价格区间（金币） |
| --- | --- | --- |
| 植物与种子 | 种子、树苗、花、作物 | 3 – 9 |
| 食物 | 熟食、面包、金苹果 | 4 – 180 |
| 武器与装备 | 铁装、钻石装、弓盾 | 5 – 4800 |
| 工具与杂物 | 各种工具、火把、命名牌 | 3 – 2400 |
| 红石机械 | 红石元件、活塞、漏斗 | 6 – 340 |
| 建筑材料 | 石料、木材、玻璃、混凝土 | 3 – 75 |
| 今日附魔书 | 每天轮换的附魔书 | 300 – 3600 |
| 冒险用品 | 末影珍珠、烈焰棒、试炼钥匙 | 45 – 1800 |

### 商品 ID 是稳定的

每个商品在 `config.yml` 里的 key 是**稳定商品 ID**：

```yaml
store:
  products:
    bread: {category: food, material: BREAD, name: '面包', price: 9, sell: true}
```

这里的 `bread` 出现在每日限额记录、交易日志和崩溃恢复数据里。

**改显示名请改 `name` 字段，不要改 ID。** 把 `bread` 改成 `mianbao`，NekoCore 看到的是一个全新的商品：额度从头开始，而旧的记录变成孤儿数据。

### 可以改的字段

| 字段 | 作用 |
| --- | --- |
| `category` | 归到哪个分类 |
| `material` | 实际给玩家的物品 |
| `name` | 显示名 |
| `price` | 每件售价 |
| `sell` | 允不允许玩家卖回来 |
| `buy-limit` | 每天最多买几件。省略 = 该物品的原版最大堆叠数 |
| `sell-limit` | 每天最多卖几件。省略 = `default-sell-limit` |

Material 必须是当前 Paper 版本里有效的、可作为物品的枚举名。拼错了重载会被拒绝，并且会给你相近名称的建议。

### 限额是怎么设计的

每个商品有两个方向的上限：

**`buy-limit`（买入限额）** —— 防的是"玩家用金币无限换资源"。默认省略时等于该物品的原版最大堆叠数，这本身就是一个自然的限制。

**`sell-limit`（出售限额）** —— 防的是"玩家用刷怪塔或农场无限换金币"。默认 200（`default-sell-limit`）。

**为什么要有售出限额：** 这是服务器经济里最容易被忽略的一个漏洞。一个设计良好的刷怪塔一天能产出上千个掉落物，如果没有限额，玩家可以把它们全变成金币，通胀会快得让你措手不及。

对特别容易刷的东西，单独设小一点的 `sell-limit` 通常比调低全局回购比例更精准：

```yaml
store:
  products:
    echo_shard:
      category: special
      material: ECHO_SHARD
      name: '回响碎片'
      price: 1600
      sell: true
      buy-limit: 4
```

限额按**玩家**计算，不是全服共享。重置和查看：

```text
/nekocore store status <玩家名>
/nekocore store reset <玩家名>
```

### 回购比例

```yaml
store:
  default-sell-limit: 200
  sell-price: {numerator: 2, denominator: 3}
```

`sell-price` 是一个分数。玩家卖东西拿到的钱 = 买入价 × `numerator / denominator`。默认 `2/3`，大约是原价的 66.7%。

**这个比例在权衡两件事：**

- **调高** → 玩家更愿意把多余产出换成钱，但"买了再卖"的损失变小；
- **调低** → 通胀压力小，但玩家会觉得卖东西不值，可能干脆把东西扔了。

**⚠ 有一条硬性上限：卖价永远不能高于买价。** `numerator` 大于 `denominator` 会被直接拒绝（报"卖价不能高于买价"），所以你最多只能调到 `1/1`。这个约束存在的意义就是堵死"买进再卖出获利"的套利路径——商店不能变成一个印钞机。

对大多数朋友服来说，`2/3` 是个舒服的位置。真正的通胀来源通常不是这个比例，而是**某些商品太容易刷**——那种情况用 `sell: false` 或者小 `sell-limit` 解决。

### 每日附魔书

附魔书是一个每天轮换的特殊商品，值得单独讲。

**每天有哪些书：**

- **2 本原版最高等级**的书；
- **6 本低阶**的书（等级 I~II，且严格低于原版最高等级）。

**什么时候换：** 北京时间 **04:00** 自动换新。批次和购买状态保存在数据库里，所以重载配置**不会**重置当天的批次。

**怎么定价：**

```yaml
store:
  enchantments:
    maximum-price: 1800      # 最高等级档
    normal-price: 300        # 低阶档
    prices: {mending: 3600, silk_touch: 2400, infinity: 2400, swift_sneak: 2700, wind_burst: 3600}
```

`prices` 里写的是**每一本的覆盖价**（不乘等级）。没写进去的书用上面两个档位价。

**诅咒附魔永远不进池子。** `excluded: [binding_curse, vanishing_curse]` 这两项别动。

**附魔书不回收。** 商店里会显示"不回收"，玩家没法买来再卖回去刷钱。

想立刻换一批：

```text
/nekocore store refresh-enchants
```

正常运营不需要这条命令——它主要用于测试，或者你刚改完附魔价格想立刻看到效果。

## 安全交易与恢复

商店和 Bag 的操作走数据库事务，并且带恢复阶段记录。

这里有一个**必须理解的现实约束**：

> 玩家的物品栏和数据库**无法成为同一个原子事务**。

这不是 NekoCore 的实现问题，而是 Minecraft 服务器架构本身的限制。玩家背包存在于服务器内存和 world playerdata 里，数据库是另一个世界。中间任何一步崩溃——服务器被杀、磁盘满、断电——都可能造成"给了物品但数据库没记"或者反过来。

NekoCore 的做法是：把一次交易拆成有名字的阶段（`BEFORE` → `UNCERTAIN` → `APPLIED`），每一步都留下记录。启动或者玩家登录时检查有没有未完成的交易，然后**根据记录判断该往哪个方向收尾**：

- 如果找到了"物品确实已经交付"的证据 → 把交易正式标记为完成；
- 如果证据表明没有交付 → 完整回滚（退回金币、归还限额）；
- **如果证据不足以判断** → **转入人工核对**，不做任何猜测。

第三种情况值得特别说明。

### 什么是"人工核对"（quarantine）

当一次交易的状态无法确定时——比如玩家背包的内容既不符合"交付前"也不符合"交付后"，通常意味着中间有**另一个插件**动过它——NekoCore 会**拒绝猜测**：

- 日志里记一条"物品记录需要人工核对，**未重发或覆盖物品**"；
- 那个玩家会看到一条提示："有一笔物品记录需要核对，暂时无法继续交易或取放 Bag。请联系管理员，物品记录已保留。"
- **物品数据原样保留，不会被重发、覆盖或退款。**

**关键的一点：这个玩家不会被封禁，可以正常游玩。** 他只是在问题解决之前不能发起任何 NekoCore 的交易、也不能打开商店和 Bag。这个设计是有意的——出问题的时候，宁可让一个功能暂时不可用，也不要擅自重放一笔不确定的操作。

源码注释里把这条原则写得很直白：模糊的、涉及第三方插件的存储故障**只隔离，不重放**；不要猜、不要退款、不要给物品、不要覆盖 Multiverse 的世界背包。

**遇到这种情况该怎么办：** 这是一个需要人工判断的场景。保留现场，比对玩家的背包、金币余额、商店额度和交易日志，然后决定怎么处理。**不要**试图通过删表或者改数据来"让它过去"。

### 关停时的处理

服务器正常 `stop` 的时候，NekoCore 会尝试收尾进行中的交易：

| 阶段 | 关停时的处理 |
| --- | --- |
| 已确认交付 | 标记为完成 |
| 明确未交付 | 回滚 |
| **不确定** | **什么都不做，留给下次登录恢复** |

第三种情况是刻意的——因为无法确认玩家背包的 `saveData()` 到底成功没有，硬猜反而可能造成复制或丢失。如果关停日志里出现"交易关停核对未完成，已保留恢复记录"，这是正常的保护行为，不是故障。

### 几条规则背后的原因

| 规则 | 原因 |
| --- | --- |
| 不要绕过 GUI 直接编辑表 | 恢复逻辑的判断依据就是那些表 |
| 不要热卸载插件 | 进行中的事务会失去收尾的机会 |
| 不要在运行时替换数据库 | 保证会损坏 |
| 备份要同时覆盖数据库**和**玩家背包 | 数据库回滚和物品回滚必须同一时点 |
| 重启前让服务器正常 `stop` | 给恢复逻辑一个干净的收尾机会 |

### 遇到未完成操作时

如果启动时发现有待恢复的操作：

1. **保持服务器离线。**
2. **保存完整副本**（`plugins/NekoCore/` 全目录 + 相关的玩家背包数据）。
3. **让恢复逻辑处理。** 启动服务器，它会尝试收尾。
4. **恢复后核对**：玩家背包、金币余额、商店额度、交易日志。

**不要做的事：** 反复更换 JAR 试错、删除交易表、手工"修" pending 记录。这些都会让可恢复的状态变得不可恢复。

完整的备份与恢复流程见[数据库文档](DATABASE.md)。

## Bag

Bag 是一个**数据库保存的、跨世界跟着玩家的物品容器**。

### 两个配置

```yaml
bag:
  enabled: true
  writable-worlds: [world]
  unlock-levels:
    '27': 10
    '36': 25
  readonly-notice-seconds: 4
```

**`enabled`** 控制入口。关掉之后 `/bag` 会提示功能停用，但**玩家的物品不会被删除**——重新打开就还在。

**`writable-worlds` 是白名单。** 列表里的世界可以取放，**其他所有世界一律只读**——包括大厅，也包括你以后新加的任何世界。

这个"默认只读"的语义很重要：**新增世界的时候它会自动是安全的**，不需要你记得去改配置。

**`unlock-levels`** 控制槽位容量。默认的映射是：

| 等级 | Bag 容量 |
| --- | --- |
| 1 – 9 级 | 18 格 |
| 10 – 24 级 | 27 格 |
| 25 级以上 | 36 格 |

用等级解锁格子是个温和的成长激励——玩家会为了多几格空间去练级。

**`readonly-notice-seconds`** 是只读世界那条提示的显示时长。

### 什么时候需要 Bag

Bag 解决的是这个问题：**玩家的随身空间不够，但又不想为了存东西跑回家。**

它和末影箱的区别在于：Bag 是**跨世界共享的**（在白名单世界里），而且容量随等级增长，并且不占用玩家的物品栏。

### 和 Multiverse-Inventories 共存

如果你用 Multiverse-Inventories 做了"不同世界独立背包"的规则，那么 Bag 如果全图可写，玩家就能把贵重物品塞进 Bag 穿过世界边界，**绕过你的规则**。

`writable-worlds` 白名单就是为这个场景准备的：只让生存世界可写，其他世界只读。

**共存时建议在测试服验证这些场景：**

- 跨世界切换时 Bag 的状态是不是符合预期；
- 玩家死亡时 Bag 内容是否受影响；
- 玩家断线重连后 Bag 还在不在；
- 背包满的时候往 Bag 里放东西会怎样。

这些组合**不在自动测试的保证范围内**。

## 头衔

Yuki、Momo、Neko 是三个通用的默认头衔预设。

| 显示名 | 稳定 ID | 价格 | 档位 | 权益 |
| --- | --- | --- | --- | --- |
| Yuki | `mame` | 2500 | 1 | 自动签到、传送冷却 120 秒、挂机 EXP ×1.10 |
| Momo | `momo` | 7500 | 2 | 自动签到、安全聊天颜色、传送冷却 60 秒、挂机 EXP ×1.10 |
| Neko | `sora` | 20000 | 3 | 自动签到、安全聊天颜色、传送冷却 30 秒、挂机 EXP ×1.20 |

### 三条设计规则

**1. 权益按已拥有的最高档位给。**

玩家买了 Neko 之后换戴 Yuki 的外观，传送冷却仍然是 Neko 的 30 秒。**随便换戴不会吃亏**，这让头衔真正变成了"外观选择"而不是"数值取舍"。

**2. 当前装备项只决定外观。**

玩家不会因为换头衔而丢失任何已购买的权益。

**3. 头衔小铺只由管理员打开。**

`/nekocore levelshop open <player>`，没有玩家自己的命令。这是有意设计的——头衔小铺被定位成"在特定地点提供"的功能，通常配合一个 NPC 或者大厅里的某个位置使用。

`levelshop.worlds` 限制哪些世界允许打开，默认只有 `world`。

### 可以改什么，不可以改什么

**可以改：** 显示名、前缀、图标、槽位、档位、价格、权益开关和数值、说明文字。

**不可以改：** `mame`、`momo`、`sora` 这三个 key。它们是稳定头衔 ID，玩家的购买记录挂在上面——和商品 ID 是同一个道理。

`rank` 字段（1/2/3）决定谁是"最高档位"。改它等于重新定义权益阶梯，改之前想清楚。

### 权益权限节点

```yaml
levelshop:
  permissions:
    auto-checkin: nekocore.perk.auto-checkin
    colored-chat: nekocore.perk.colored-chat
    fast-tpn: nekocore.perk.fast-tpn
```

这三个节点默认都是 `false`。如果你想用权限插件直接授予权益（比如做"VIP 直接送自动签到"），改这里的名字对齐你的权限命名规范就行。

## 周金币榜

```yaml
weekly-coin-leaderboard:
  enabled: false
  position-configured: false
```

榜单统计的是**本周的金币收入**，不是当前余额。

**周从周一开始。** 一个"周"的边界是**北京时间周一 00:00**（这个时区是固定的，不跟随任何配置）。所以周日 23:59 赚到的钱算上一周，周一 00:00 之后算新的一周。

**哪些收入算进去：** 签到、每日任务、挂机池、商店出售。

**哪些不算：** 管理员手动加的金币（`/nekocore coins add`）、商店买入的支出、以及交易恢复/回滚相关的变动。

所以这个榜单衡量的是"**这周谁通过正常玩法赚得最多**"——管理员发的奖励刷不出榜首，一个富有的老玩家如果这周没赚过钱也不会自动霸榜。

**两把锁：** `enabled` 和 `position-configured` 都要 `true` 才会生成显示。

**但统计是独立于显示的：** `position-configured: false` 的时候统计**照常进行**，只是不生成 TextDisplay，并记一条 WARNING。所以你可以放心先开着 `enabled: true` 收集数据，等想好挂哪儿了再补坐标。

**并列时的排序：** 收入相同时按 UUID 升序排列。榜上显示的名字取的是**当前**名字，所以玩家改名后榜单会跟着变。

排序和显示逻辑保留了 schema 5 的周收入结构。
