# 安装、升级、回滚与卸载

[English](../en/INSTALLATION.md) | [返回 README](../../README.md)

[快速开始](QUICKSTART.md)讲的是"第一次开服怎么走通"。这一页讲的是**服务器已经存在之后**的那些事：全新安装的完整流程、从旧版本升上来、出问题怎么退回、以及不想用了怎么干净地拿掉。

第一次开服的话，先看快速开始，再回来看这一页的升级章节。升级和备份的内容建议在上线**之前**就读一遍——等出事的时候再学怎么恢复，通常已经晚了。

---

## 全新安装

### 前提

| 需要 | 版本 |
| --- | --- |
| [Paper](https://papermc.io/downloads/paper/) | 26.2 |
| [Java](https://docs.oracle.com/en/java/javase/25/install/) | 25 |
| NekoCore | `NekoCore-1.2.0.jar` |

Java 装完用 `java -version` 确认第一行是 25。Paper 首次启动的 EULA 流程见快速开始。

### 步骤

1. **先让 Paper 自己跑一次。** 不装任何插件，启动到出现 `Done`，然后 `stop`。这样服务器的基础文件、世界、`server.properties` 都由 Paper 自己生成好，是最干净的状态。

2. **停服状态**下，把 `NekoCore-1.2.0.jar` 放进 `plugins/`。

   **不要**放 `original-NekoCore-1.2.0.jar`（那是 shade 打包前的半成品）。如果你还想装 PlaceholderAPI、Citizens 或 Multiverse-Core，现在一起放进去，顺序无所谓——但**不装也完全没问题**。

3. **启动。** 首次启动时 NekoCore 会：
   - 在 `plugins/NekoCore/` 生成 `config.yml` 和 `messages.yml`；
   - 创建 `nekocore.db` 并执行 V1→V5 迁移建表；
   - 打印一段简短的状态摘要。

   日志里应该能找到一行包含 `NekoCore 1.2.0 ready` 的摘要。**日志被有意压缩过**，不会刷满屏幕；没有 `ERROR` 就是正常的。

4. **停服**，编辑 `plugins/NekoCore/config.yml`。至少改 `branding.server-name`；主世界不叫 `world` 的话，`survival.world` 也要改。

5. **重启**，进游戏验证。`/menu`、`/checkin`、`/sethome`、`/home`、`/coins`、`/store`、`/bag` 都试一遍。管理员再跑 `/nekocore status`。

第一次做这几步的话，[快速开始](QUICKSTART.md)里有更细的说明——包括 `plugins` 文件夹在哪、用什么编辑器、YAML 缩进为什么不能乱、以及一份开服前的检查清单。

### 首次启动不需要准备什么

这一点值得单独说，因为很多人会在这里过度准备：

- **不需要** PlaceholderAPI、Citizens、Multiverse-Core；
- **不需要** GeoLite2 数据文件；
- **不需要**第二世界、小游戏地图、展示坐标或 NPC。

NekoCore 首次启动只需要 Paper 和 Java。缺什么就安静地关掉什么，其余功能照常。等你真的需要某个功能了再回来配。

### 一条习惯

**不要在插件启动的过程中覆盖配置文件或 JAR。** 听起来是常识，但在面板类服务器上"上传即生效"的操作很容易让人不经意在服务器运行时换了 JAR。养成"要动文件就先 `stop`"的习惯。

## Public 1.1.0 → 1.2.0

完整停服、备份旧 JAR 和整个插件数据目录（数据库含 WAL/SHM、世界玩家背包），只替换 JAR。保留 config.yml / messages.yml / 数据库；本次仍是 config 9、messages 8、schema 5，没有新增 YAML / 数据库迁移。缺少的 lookup 文案在内存中补默认，不重写旧文件。预设只在缺失时复制，不自动应用，不覆盖已有预设。普通重启不重复首次配置指引。详见[预设](PRESETS.md)。

下面保留 1.0.0 → 1.1.0 的历史迁移说明；从 1.0.0 直升 1.2.0 仍使用这套原有迁移机制与备份名。

## Public 1.0.0 → 1.1.0

在**服务器机器**操作，先完整停服并备份旧 JAR、整个 `plugins/NekoCore/` 和世界玩家背包数据；存在 WAL/SHM 时与数据库一起备份。然后移走旧 JAR，只放 `NekoCore-1.2.0.jar`，**不要覆盖或删除自己的 config.yml / messages.yml / nekocore.db**。

首次启动会合并缺失字段，并仅将与 Public 1.0 默认快照完全相同的字段更新为新默认；管理员不同的 server-name、商品、任务规则、TAB、Tips、世界、槽位、文字、links、奖励值都保留。原 YAML 逐字节备份为 `*.yml.pre-public-1.1.0-<随机标识>.bak`。新增 JoinInfo 默认开启但四个链接为空；AFK、Mascot、排行榜的默认关闭状态不变。

内部版本变化：config **8 → 9**，messages **7 → 8**，因为增加 JoinInfo、billboard、AFK 结束提示等字段，需要现有迁移系统补全；SQLite schema **仍为 5**，V1→V5 保留，不新增 V6。旧迁移快照仍全部存在，但其中旧部署标题和坐标已通用化；来自更早私有配置的这些值可能按自定义值保留，请管理员自行审核，插件不会擅自覆盖未知部署设置。

启动后运行 `/nekocore config check`、`/nekocore status` 和 `/nekocore doctor`。用玩家检查 `/tasks`、个人 JoinInfo 和已有数据；开启了对应模块的测试服还应检查排行榜 yaw、Mascot 高度、AFK 宽限及结束消息。默认未自定义的 Tips 改为 180 秒、AFK 奖励尝试改为 60 秒。回滚时恢复**同一份停服备份中的 JAR、YAML、数据库和背包数据**，不要只换旧 JAR。

## 从 NekoCore 1.4.0 / 旧版本升级

Public 1.0.0 最初基于完整的私有 1.4.0；Public 1.1.0 在该公版仓库上增量同步 1.4.1～1.4.4 的通用能力，没有推倒重写。两条版本线独立，私有 1.4.4 不等于 Public 1.1.0。旧版本升级仍须测试备份和数据恢复，不应仅凭共同基线就判断为低风险。

### 步骤

1. **让玩家离线，然后在控制台执行 `stop`，等 Java 进程完全退出。**

   不要只看控制台不响应了就以为停好了。确认进程真的结束了（任务管理器、`ps`、或者面板上显示"已停止"）。

2. **做一份完整的备份。** 至少包含：
   - 旧的 NekoCore JAR；
   - 整个 `plugins/NekoCore/` 目录；
   - 与背包相关的 world playerdata，以及 Multiverse-Inventories 的数据（如果你在用）。

3. **⚠ 关于 `.db-wal` 和 `.db-shm`。**

   如果 `plugins/NekoCore/` 里同时存在 `nekocore.db-wal` 或 `nekocore.db-shm`，**必须和 `nekocore.db` 一起备份**。

   只复制 `.db` 可能拿到一个不完整的时点——最近提交的事务可能还在 WAL 文件里。**绝对不要在服务器运行时只复制 `.db`。**

4. **从 `plugins/` 移走旧 JAR**，只放入 `NekoCore-1.2.0.jar`。**保留现有的 `plugins/NekoCore/` 目录**——配置和数据库都在里面，这正是你要延续的东西。

5. **完整启动**，观察日志：
   - 配置升级的备份信息；
   - V1→V5 的迁移记录（旧库只执行缺失的版本）；
   - `NekoCore 1.2.0 ready`。

6. **运行 `/nekocore status`**，确认 schema 是 5、各模块状态正常。

7. **逐项核对玩家数据。** 按这个清单过一遍：

   - [ ] 金币余额
   - [ ] 累计经验与等级
   - [ ] 各世界的 Home 坐标
   - [ ] 签到记录（今天领过没有）
   - [ ] 隐私开关状态
   - [ ] 已拥有的头衔、当前装备的头衔
   - [ ] Bag 里的物品
   - [ ] 商店的每日额度
   - [ ] 附魔书批次和已购买次数
   - [ ] 交易日志
   - [ ] 游玩时长、首次/最近加入时间
   - [ ] 每日任务进度
   - [ ] 本周金币收入

### 关于版本号

**Public 版本号 1.1.0 不会重置内部版本。** 也就是说：

| 内部版本 | 值 |
| --- | --- |
| `config-version` | 9 |
| `messages-version` | 8 |
| SQLite `user_version`（schema） | 5 |
| 迁移 | V1、V2、V3、V4、V5 |

**本版没有 V6。** 如果你在旧库或者文档里看到 V6 的说法，那是不对的。

**为什么这些数字不能动：** 它们决定了插件怎么看你的数据。把 `config-version` 从 8 改成 7 并不会"修复"任何问题，只会让插件按一套错误的规则去读你的文件。

### 数据比插件新的时候会怎样

如果数据库的 schema 版本**高于 5**（比如你曾经装过一个更新版本的 NekoCore，现在退回来了），插件会**拒绝打开数据库**。

这是保护，不是故障。用一个旧的插件去写一个更新的数据结构，后果可能是静默地损坏玩家数据——相比之下，拒绝启动并明确报错要好得多。

### 旧配置里的新增字段

旧版本的 `config.yml` 里不会有 Public 版新增的那些门闩（比如 `position-configured`）。这种情况下 NekoCore 会**采用兼容旧行为**的方式处理，不会因为缺字段就崩掉。

而全新生成的 Public 配置使用安全默认——那些新门闩默认是 `false`。

**建议：** 升级之后，把新生成的默认文件和你的旧文件**逐项比较**一遍，看看有没有值得采纳的新字段。不要直接扔掉自己长期积累的自定义，也不要因为"文件能跑"就完全忽略新字段。

### 一条边界

从真实备份升级这件事，**自动测试只能覆盖到一定程度**。数据库层、配置升级层和插件契约有测试覆盖（包括一个从全空目录开始的 fresh install 场景），但"你这台具体的服务器、这套具体的插件组合、这份具体的历史数据"仍然需要你实机验证一次。

在测试服上先升一遍，是最省心的做法。

## 回滚

**不能只把旧 JAR 换回去。** 这是回滚里最重要的一句话。

原因很简单：新版本的 NekoCore 可能已经动过你的数据库（执行了迁移、写了新表）。单独换回旧 JAR 会让它面对一个它不认识的结构。

### 正确的回滚方式

1. **停服**，等进程完全退出。
2. 恢复**同一个时点**的四样东西：
   - 旧 JAR
   - 旧配置（`config.yml`、`messages.yml`）
   - 旧数据库（含 WAL/SHM）
   - 涉及 Bag / Store 时的玩家背包数据（world playerdata、MVI 数据）
3. **先在副本上验证**，确认能正常启动、数据完整，再对正式服操作。

### 最常见的回滚错误

| 错误做法 | 会出什么事 |
| --- | --- |
| 只换 JAR，不换数据库 | 旧插件读到更新的 schema，可能拒绝启动或者写坏数据 |
| 换了数据库，没换配置 | 配置里的字段和数据库结构对不上 |
| 换了数据库和配置，没管背包 | Bag/Store 的物品和数据库记录对不上，出现复制或者丢失 |
| 只恢复了 `nekocore.db`，漏了 WAL | 拿到一个较早的、可能不完整的时点 |

**配置备份不是数据库备份，数据库备份也不是物品备份。** 这三样东西必须来自同一个时点。

## 卸载

1. **停服**，等进程完全退出。
2. 把 `plugins/NekoCore-1.2.0.jar` 从 `plugins/` 移走。
3. **`plugins/NekoCore/` 目录建议保留。** 它在插件被移除后不会造成任何影响，但如果你想以后回来，配置和玩家数据都还在。

### 移除之后会发生什么

卸载插件**不会**自动撤销任何已经产生的外部影响：

- 已经发到玩家背包里的物品还在；
- 已经加进玩家账户的金币不会消失（如果那些数值被别的插件记录了）；
- 别的插件保存的显示状态（TAB 内容、聊天前缀）可能残留。

**删除 Citizens NPC 也要你自己在 Citizens 里做。** NekoCore 从不创建、移动或重命名 NPC，所以它也不会替你删。

上线之前把卸载流程在测试服走一遍，是值得的——尤其是当你的服务器已经有一些依赖 NekoCore 数据的其它插件的时候。
