# 数据库、迁移与数据安全

[English](../en/DATABASE.md) | [返回 README](../../README.md)

这一页讲的是 NekoCore 的数据层：数据存在哪、升级的时候发生了什么、怎么备份、出问题怎么恢复。

**这一页不用卖萌，也不会卖萌。** 数据丢失是开服过程里最不可逆的一类事故，值得用最清楚的措辞讲。

---

## 数据存在哪

一个 SQLite 文件：

```text
plugins/NekoCore/nekocore.db
```

同一个目录下还可能出现两个伴生文件：

```text
plugins/NekoCore/nekocore.db-wal    ← 预写日志
plugins/NekoCore/nekocore.db-shm    ← 共享内存索引
```

**这两个文件不是垃圾，也不能单独删除。** 它们是 SQLite 的 WAL 模式产生的正常组成部分。最近提交的事务可能还在 `.db-wal` 里，还没有合并进主文件。

**备份的时候，这三个文件必须一起复制，而且必须是同一个时点的。** 只复制 `.db` 可能拿到一个缺失最近更改的旧时点——这是最常见的"备份看起来正常但恢复后少了几小时数据"的原因。

数据库里装着：

| 内容 | 说明 |
| --- | --- |
| 玩家资料 | UUID、名字、首次加入、最近加入、游玩时长 |
| 经济 | 金币余额、累计经验、等级 |
| Home | 每个世界各自的坐标 |
| 签到 | 每日签到记录 |
| 头衔 | 已拥有的头衔、当前装备的头衔 |
| Bag | 随身容器里的物品 |
| 商店 | 每日购买/出售额度、交易日志 |
| 每日任务 | 全服 rotation、每个玩家的进度 |
| 周金币 | 本周收入统计（供周榜使用） |

**它包含玩家 UUID 和游戏数据，属于敏感的运营数据。** 不要放进公开的 issue、Git 仓库、Release 附件或测试文件里。需要别人帮忙排查的时候，生成一个最小化的、脱敏过的复现库。

## 版本与迁移

Public 1.0.0 的 `PRAGMA user_version` 是 **5**。迁移脚本保留了 V1 到 V5：

| 迁移 | 内容 |
| --- | --- |
| V1 | 初始玩家资料、经济、Home 等基础表 |
| V2 | 每日签到 |
| V3 | 商店、Bag、头衔与安全交易相关结构 |
| V4 | 每日任务 rotation 与 progress |
| V5 | 周金币收入与排序索引 |

**本版没有数据库 V6。** 迁移 SQL 文件在 JAR 里，不要删除或修改它们。

> **别把数据库迁移和配置快照搞混。** JAR 里还有一组 `src/main/resources/migration/vN-config.yml` 和 `vN-messages.yml`，它们是**历史配置格式的快照**，用来升级旧的配置文件。这组文件一直到 `v6-config.yml` 和 `v7-config.yml`。它们和数据库结构没有关系——数据库停在 V5，而当前的配置格式是第 8 版。**看到 `v6-config.yml` 是正常的，它不代表存在 V6 迁移。**

### 迁移怎么跑

- **全新的空目录：** 按 V1 → V2 → V3 → V4 → V5 的顺序在事务中依次执行。
- **已有的旧库：** 只执行缺失的版本。一个 schema 3 的库只会跑 V4 和 V5。
- **版本高于 5 的库：** **拒绝启动数据库。**

最后一条是刻意的保护。用一个旧的插件去写一个更新的数据结构，可能造成静默的数据损坏——相比起来，明确地拒绝启动、在日志里告诉你原因，是更好的结果。

### 事务与恢复

SQLite 由**单一的后台 executor 线程**拥有。Bukkit 对象不会跨越这条边界，也就是说数据库操作不会和你服务器的主线程互相踩。

提交事务之后才更新内存里的玩家资料——这个顺序保证了"数据库里有什么，游戏里就认为有什么"。

**Store 和 Bag 使用恢复记录。** 这里需要理解一个现实约束：

> 玩家的物品栏和数据库**无法成为同一个原子事务**。

这是 Minecraft 服务器架构本身的限制，不是 NekoCore 的实现问题。玩家背包是服务器内存和 world playerdata 里的东西，数据库是另一个世界。中间任何一步崩溃（服务器被杀、磁盘满、断电），都可能出现"物品给出去了但数据库没记"或者反过来的情况。

NekoCore 的做法是：在操作前后写下恢复阶段记录，启动时检查有没有未完成的操作，然后**朝一个确定的方向收尾**——要么完整交付，要么完整撤销，不留中间状态。

这也是为什么**不要手工编辑数据库表**：那些 pending 表和 transaction 表看起来像碍事的历史记录，实际上正是恢复逻辑的判断依据。手动清空它们，等于把恢复机制的眼睛蒙上。

### 不要开第二个实例

不要让**两个服务器实例同时打开同一个数据库文件**。SQLite 的文件锁不应该被当成跨进程协调机制来用。多服网络共享一份 NekoCore 数据不在设计目标内。

## 备份

### 正确流程

1. **在控制台执行 `stop`。**
2. **等 Java 进程完全退出。** 确认进程列表里真的没有了，或者面板显示"已停止"。控制台不响应 ≠ 进程已退出。
3. **复制整个 `plugins/NekoCore/` 目录。** 这样自然会把 `.db`、`.db-wal`、`.db-shm`、`config.yml`、`messages.yml` 一起带走，省得漏。
4. **如果你在用 Store 或 Bag**，还要复制**同一个时点**的：
   - world playerdata（玩家背包）
   - Multiverse-Inventories 数据（如果装了）

5. **归档到一个和服务器不同的地方。** 同一块磁盘上的备份在磁盘故障时没有意义。

### 为什么物品数据要和数据库同一个时点

因为 Bag 和 Store 的操作跨在两边。你恢复了昨天的数据库，但用了今天早上的玩家背包，就会出现：

- 玩家昨天买的东西，数据库认为交易已完成、金币已扣，但背包里的物品来自一个没有那笔交易的时点；
- 或者反过来，数据库里的 Bag 内容包含一组物品，而背包数据里那组物品也还在。

**数据库回滚和物品回滚必须是同一个时点。** 这也是前面反复强调"停服、等进程退出、一起复制"的原因。

### 定期做恢复演练

**只确认压缩包存在，不等于备份可用。**

建议每隔一段时间做一次真实演练：在一个临时目录搭一个测试服，把备份恢复上去，启动，进游戏确认玩家的金币、Home、Bag 都在。

演练的价值在于发现那些"备份文件其实早就损坏了"或者"我漏了某一类数据"的问题——在你真的需要备份之前。

## 恢复与排障

### 遇到问题时

1. **先复制故障现场。** 在动手修之前，把当前的 `plugins/NekoCore/` 完整复制一份到别处。这样最坏的情况下你还能回到"故障但可分析"的状态。
2. **只在副本上做实验。**
3. **保持服务器离线**，直到你搞清楚发生了什么。

### 绝对不要做的事

| 做法 | 为什么不行 |
| --- | --- |
| 删除迁移 SQL | 新库会建不出来，旧库的下一次迁移会失败 |
| 修改 `user_version` | 让插件按错误的版本假设读你的数据 |
| 清空 pending / transaction 表 | 破坏恢复逻辑的判断依据，可能把可恢复的状态变成不可恢复 |
| 用 GUI SQLite 编辑器"修复"数据库 | 这类工具不了解 NekoCore 的事务语义，容易写出不自洽的状态 |
| 反复替换 JAR 试错 | 每次启动都可能触发迁移；在没有备份的情况下这很危险 |
| 在服务器运行时替换数据库文件 | 保证会损坏 |

### 常见故障的方向

**磁盘满。** 先停服。SQLite 在磁盘满的时候写入会失败，可能留下不完整的 WAL。腾出空间后重启，让恢复逻辑处理。

**文件权限错误。** 停服，修正 `plugins/NekoCore/` 的读写权限，再启动。Linux 上注意运行服务器的用户和文件属主是否一致。

**数据库被锁。** 通常意味着有第二个进程打开了它。检查是不是有残留的服务器进程，或者某个 SQLite 浏览器正开着这个文件。

**schema 版本过高。** 你装了一个更新版本的 NekoCore 又退回来了。恢复那个新版本的 JAR 和数据，或者回到升级前的备份。

**数据库损坏。** 停服，保留现场，从备份恢复。**不要在原始文件上尝试修复**——先把原文件留住，任何时候都能再分析。

### 从旧版本恢复时

必须恢复**同一时点**的四件套：

```text
JAR + 配置 + 数据库 + 物品数据
```

任何一样来自不同的时点，都可能产生对不上的状态。

---

## 小结

如果这一页只记三句话：

1. **备份要停服，`.db` / `.db-wal` / `.db-shm` 和物品数据要一起复制。**
2. **恢复要恢复同一时点，先在副本上验证。**
3. **不要手工改数据库，那些看起来多余的恢复表是在保护你。**
